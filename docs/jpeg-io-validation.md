# JPEG I/O validation — 2026-09-17

This step for issue #43 replaces the memory source's unconditional 4096-byte
copy with an explicit complete input span. Each refill copies only remaining
bytes. A single synthetic EOI is permitted only at true EOF; empty input,
repeated EOF and marker skips beyond real bytes fail through the operation's
error handler. The standard FILE source API is restored for bundled tools,
and the unused, unsafe standalone `jload.c` implementation is removed.

The renderer owns JPEG state in a heap context with a private error manager.
Decoder/library errors return via setjmp/longjmp, destroy even partial codec
state and release input/output buffers before ERR_DROP. Missing files stay
quiet. Successful loading publishes dimensions and opaque RGBA only after
finishing the complete decode. Standard RGB library rows and grayscale rows
expand backwards within a single checked RGBA allocation; screenshots strip
RGBA into RGB rows without changing caller pixels. This also supports tagged
RGB streams. CMYK and progressive decoding remain unsupported by this bundled
configuration and reject with cleanup.

Screenshot storage starts at 4096 bytes and grows before a full destination
is reused. Growth preserves all encoded bytes and has an explicit signed
allocator limit. Only finished encoding calls FS_WriteFile, once, with its
actual byte count; the preliminary one-byte screenshot write is removed.
There is no global byte-count state. Allocation failures returned by the
import API clean up without publishing a partial screenshot. The engine's
normal zone allocator still treats actual heap exhaustion as fatal; this
change does not introduce a general nonfatal allocator.

Dimensions and buffer products reserve 4096 bytes below INT_MAX for native
allocator headers/alignment, also used by BMP/TGA output bounds. JPEG's native
65500-axis limit is retained. Both bundled allocation hooks reject oversized
requests before narrowing to the renderer's int API. Standard Huffman setup
copies only defined symbols, bit accumulation uses unsigned shifts, and
malformed Huffman counts/trees/DC symbols reject before table writes or
bit extraction. DHT indices validate before forming array pointers; unused
symbol slots are initialized.

The sole definitions of jpeg_start_compress/jpeg_write_scanlines remain in
jcapistd.c. CMake, Unix Make/Cons, Visual Studio and every Xcode renderer phase
include it and the portable JPEG renderer module; lint includes the module.
The build-manifest regression covers both required sources. Source selection
no longer depends on linking one of two conflicting compressor definitions.

The private recovery approach follows the application's ownership model
explained by [libjpeg-turbo's example](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/src/example.c).
Huffman bounds follow the validity conditions documented in its
[decoder](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/src/jdhuff.c).
These comparisons do not claim a complete advisory audit of the old library.

## Validation

A standalone public-header compile check and ASan/UBSan run the actual portable renderer and the complete bundled codec.
Input allocations end exactly at four alignments. Cases cover every prefix
of a small real JPEG, all invalid input sizes 0–4095, actual valid files and
source refills around 4096/8192, marker skips crossing EOF, repeated/empty
EOF, golden RGB/YCbCr/grayscale pixels, opaque alpha and optional dimensions.
Malformed tables, oversized/zero dimensions and negative lengths reject
without published output or leaked file/codec storage. Standard FILE decoding
leaves stream ownership with its caller. Unsupported color/progressive files
are generated by the real encoder and rejected by the loader.

A 1×1 screenshot encodes to more bytes than its raw RGBA input. A noisy
128×128 screenshot requires multiple destination growths and decodes to its
expected flipped pixels. Injected failure at every load/save allocation
checks cleanup before errors/warnings, no partial file write and unchanged
caller pixels. Direct allocation-hook and output-capacity guards reject
fictitious huge spans before reading or allocating them. BMP/TGA regressions,
Python tests and both Mac products are checked after the final source changes.

Nine Python tests, all affected image fixtures and Bash syntax pass. Both
Retro68 products build without compiler diagnostics and validate as PPC PEFs
using the temporary loader libraries recorded in [loading evidence](qvm-loading-validation.md).
